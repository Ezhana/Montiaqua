# 0001. 按"本地每天跑"把 infra/ 与 deploy/ 切开

- 状态：已接受
- 日期：2026-11-02
- 相关：[infra/README.md](../../infra/README.md)、[deploy/README.md](../../deploy/README.md)

## 背景

仓库同时需要两类环境配置：本地开发要能一条命令拉起依赖、直连端口、灌种子数据；staging / prod 要能由平台和发布流程消费一份只引用镜像的清单。

比"文件名里带 dev 还是 prod"更可靠的界线，是执行者：谁每天运行这份文件。本地开发者每天跑的东西，可以为了速度放宽（直接构建、弱口令、端口直通、种子数据）；只在发布时被平台消费的东西，必须收紧（只认镜像、不装依赖、密钥外部注入）。

## 决策

- `infra/` 只服务本机开发，允许 `build:`、弱密钥、端口直通和 seed 数据；不得出现真实密钥、云上地址与发布逻辑。
- `deploy/` 只服务非本地环境，只引用 `image:`；不 build、不装依赖，密钥在运行时由外部注入。
- 判断标准：**这份文件会不会被本地开发者每天跑？** 会 → `infra/`；不会（只在发布时被平台消费）→ `deploy/`。
- 两层不共享文件、不共享变量；同一份编排不能既 build 又部署。
- 未来引入 Terraform / 云资源定义时，放 `infra/terraform/`（或独立 `platform/`），不要和应用清单混进同一层。

## 后果

- 好的方面：本地体验不被生产约束拖慢；部署清单保持镜像化、可审计，不会因为本地调试需要而混入构建步骤。
- 代价：镜像构建必须落在项目与 CI 侧，本地 compose 与部署清单需要各自维护（结构可以互相参照，但不能共用文件）。
- 代价：`deploy/` 的 YAML 不能随手写 `build:`，由 CI 的层规则检查兜住；本地开发也不要往 `deploy/` 里加编辑入口。

## 备选方案

- 单目录按环境分子目录（`deploy/local`、`deploy/staging`）：文件仍在同一层，容易互相挪用变量和构建步骤，判断标准模糊，放弃。
- 本地配置全放各项目目录：本地依赖的编排是跨项目的，散落各项目会重复且难统一，放弃。
